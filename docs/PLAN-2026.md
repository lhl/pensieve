# Pensieve 2026 Reboot Plan

*Created: 2026-02-01*  
*Status: Draft*

This repo is a long-dormant prototype. In 2026 we’re rebooting it as a modern PKMS “meta project”: ingest + triage + organization + search + selective publishing, with agent-assisted operations.

Primary design doc: `docs/PKMS-ARCHITECTURE.md`.

## Goals (2026)

- Index and search across many vault repos (private/public/shared) at 100k+ document scale
- Build a durable ingest pipeline to convert legacy exports into canonical “inbox items”
- Provide a fast triage workflow (human-in-the-loop, agent-assisted)
- Support selective publishing of notes/resources into a digital garden (likely `randomfoo.net`)
- Keep canonical knowledge in plain files (git-friendly), with LanceDB as a derived index layer

## Non-goals (for the first reboot phase)

- Fully automated “AI rewrites” of existing notes
- A monolithic database as the canonical store
- Perfect ontology/taxonomy up front

## Milestones

### M0 — Reboot docs + repo conventions

- [ ] Finalize canonical-vs-derived stance (MD canonical; DB derived)
- [ ] Lock metadata conventions (frontmatter fields, ID scheme, visibility model)
- [ ] Decide link conventions (`[[wiki]]` vs markdown links)
- [ ] Decide repo topology: one primary “everything” vault vs multiple first-class vaults
- [ ] Decide deployment topology: always-on services + local-first clients (and what must work offline)
- [ ] Do a landscape review (avoid reinventing wheels):
  - local-first/offline frameworks (PWA sync, queues/outbox, replication/CRDT options)
  - on-device search options (keyword vs semantic; constraints by platform)
  - static publishing toolchains that support incremental builds + massive redirects
- [ ] Write up findings in `docs/RESEARCH-2026-landscape.md`
- [ ] Use `docs/ANALYSIS-legacy.md` to constrain modernization choices (what to keep vs replace)
- [ ] Decide “first-class clients” approach (desktop/web/mobile) with minimal dev burden:
  - PWA-first vs Expo/React Native vs hybrid
  - capture intents/shortcuts and notification requirements per platform

Deliverable: architecture + plan docs usable by any agent/human.

### M1 — Vault spec + minimal CLI skeleton

- [ ] Define `vault.yaml` spec (vault_id, include/exclude, default visibility)
- [ ] Decide how vaults are discovered (local `vaults.yaml`, CLI flags, env var, etc.)
- [ ] Define canonical file types:
  - notes (Markdown)
  - inbox items (Markdown + raw payload)
  - attachments (file + `.meta.yaml`)
- [ ] Create a minimal CLI entrypoint (even if just scaffolding):
  - `pkms scan` (list notes across vaults)
  - `pkms search` (placeholder)
  - `pkms triage` (placeholder)

Deliverable: repository-local tooling that can enumerate vault content deterministically.

### M1b — Cross-platform client (capture + recall first)

- [ ] Implement a minimal “capture client” usable on desktop/web/mobile:
  - share/intent: URL/text → inbox item
  - quick actions: tag/visibility/project filing
  - reminders/notifications (at least local notifications; push optional)
- [ ] Implement offline outbox queue + sync to server when online
- [ ] Make “collected vs authored vs projects” first-class filters in the UI

Deliverable: fast capture + triage anywhere, without waiting for full editor rebuild.

### M2 — LanceDB indexer (derived store)

- [ ] Implement scanner → parser → chunker → embedder → upsert pipeline
- [ ] Store tables for:
  - documents (note metadata)
  - chunks (chunk text + embedding vectors)
  - links (edges)
- [ ] Incremental indexing:
  - content hashes per file
  - per-vault manifest + last indexed revision
- [ ] `.gitignore` the local DB path (keep it rebuildable)

Deliverable: semantic search across multiple vault repos on local machine.

### M3 — Ingest pipeline (legacy exports → inbox)

- [ ] Standardize “inbox item” canonical format + directory layout
- [ ] Build importers that take existing exports and create inbox items:
  - start with `attention-export` outputs
  - preserve raw payload + source metadata
- [ ] Add “event streams” canonical format (`streams/*.jsonl`) for high-volume activity
- [ ] Dedupe primitives (URL normalization, content fingerprints, source IDs)
- [ ] Add optional “bookmark + snapshot” workflow (ArchiveBox-style) with snapshot status tracking

Deliverable: tens-of-thousands of legacy artifacts land in a consistent inbox format.

### M4 — Triage workflow (human + agent)

- [ ] A fast “next item” flow:
  - propose tags, links, destinations, visibility
  - accept/reject with minimal keystrokes
- [ ] Keep AI suggestions separate from canonical edits until accepted
- [ ] Support “promote” from inbox → notes and/or across vault repos

Deliverable: sustained throughput for organizing legacy backlog.

### M5 — Publishing pipeline (digital garden)

- [ ] Decide publishing model:
  - Model A: public vault repo (recommended first)
  - Model B: export from mixed vault
- [ ] Define publishing metadata:
  - visibility, permalink/slug, publish collections
  - redaction rules / “safe export”
- [ ] Integrate with `randomfoo.net` build pipeline (likely separate repo, but coordinated)
- [ ] Support multi-site publishing targets (randomfoo.net, llm-tracker.info, leonardlin.com, other legacy gardens)
- [ ] Generate and validate large redirect sets (thousands), including per-note aliases + bulk redirect registries
- [ ] Make builds incremental: regenerate only changed pages and dependent indexes (tags, backlinks, feeds, sitemaps)

Deliverable: selective publishing of curated notes/resources with stable URLs.

### M6 — Agent daemon integration (reminders + time-sensitive)

- [ ] Define canonical task/reminder representation
- [ ] Define safe writeback rules for an agent
- [ ] Integrate with a daemon architecture (reference: `shisad`) for:
  - scheduled ingest
  - reminder delivery
  - periodic re-index

Deliverable: “always-on” PKMS operations without compromising safety/privacy.

## Key design decisions to settle early

- **ID scheme:** ULID/UUIDv7 in frontmatter vs path-derived IDs (prefer ULID/UUIDv7)
- **Visibility model:** private/shared/public/unlisted + per-vault defaults
- **Link model:** `[[id]]` (stable) vs `[[path]]` (convenient) vs hybrid
- **Attachments:** git vs Git LFS vs external store (per-vault policy)
- **Publishing boundary:** separate public vault vs export step
